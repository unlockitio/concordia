# BabyDRO: trusted-resolver canton.name governance demo

The CIPs credentials demo owns name requests and credentials. BabyDRO owns governance and member entitlement. This is an opt-in example excluded from Concordia's `multi-package.yaml`. Its CIPS interface and model are exported from locally available commit `8e36c20e5106014efb8348f749d9535afbc48921` by `prepare-dependencies.sh`, without modifying the CIPS checkout. The full model is built, including its HoldingV1 example; the missing HoldingV1 binary is obtained from an immutable official Splice URL and SHA-256 checked. See [MIGRATION.md](MIGRATION.md) for pins and interface adapters. The name model remains draft [canton-foundation/cips PR #209](https://github.com/canton-foundation/cips/pull/209), without an assigned CIP number. None of this establishes global name uniqueness: other issuers can issue names.

## Trust and visibility

A distinct DRO administers a consortium signed by itself and every current registry member. Each founder accepts separately before genesis finalization; admission needs two member approvals plus the candidate's consent, removal needs two member approvals and cannot remove a claimant while its dispute is active. Voting rights are invited by an all-member choice but issued separately on a DRO-and-holder-signed contract (direct or CIPs registered route). The consortium holds membership stints, never foreign right IDs. A right is revoked only by its issuer; it is rechecked at resolution, so expiry, revocation and a prior membership stint cannot vote. Admission after removal increments the stint.

A `NameDispute` freezes claimant credential IDs, actions, opening electorate, policy and case identity. A DRO-signed `DisputeInvitation` lets a voter enrol exactly once. `NameDispute.registered` is the monotonic roll of enrolled **voter identities**, not ballot references. Invitation acceptance checks a live right, consumes the member-observed case to enrol the voter, and creates the initial DRO-and-voter-signed `Ballot` as a sibling of that enrolment. The member-visible enrolment does not fetch the ballot or carry its CID. A cast or withdrawal consumes the prior ballot and creates exactly one private successor without exercising the case. A withdrawal means no vote until a recast. The DRO supplies the latest live slot for each enrollee at resolution; the keys must equal the entire case roll. Every fetched slot must match the case, voter, frozen state and actions. A superseded slot cannot be fetched. The case roll is participation metadata visible to consortium members.

`SnapshotAtOpen` counts votes from the frozen opening electorate, even after removal of a non-claimant; `CurrentMembership` excludes removed members. Both check eligible voters' live rights against the *current* consortium stint. The DRO-only `DisputeResolver.Resolver_Resolve` is the private tally root. It enforces a two-voter quorum for the selected winner, rejects any opposing winner with a two-voter quorum, checks agreeing Action IDs and frozen snapshots, and consumes **all** presented ballots. Its nested `Consortium_PublishRuling` child carries only the decided outcome, case ID, and a `TallyReceipt` holding the roll and outcome, not per-voter decisions or counts. The child executes the winner's pre-minted `ArchiveClaimAction`/`ArchiveClaimExecution`, archiving **all** frozen losing CIPs credentials through `Credential_ArchiveAsAnchorers`, closes the case and its actions, spends the receipt and resolver, and creates a `Ruling` visible to every member plus a member-signed consortium successor. All operations are atomic; a failed loser archive rolls them back. An archived or replaced frozen credential can deadlock resolution; no cancellation route is implemented. `Ruling_Follow` is only an acknowledgement.

**The guarantee is ballot-content privacy in the honest resolver path, not trustless counting.** In the local LF 2.3 transaction projections inspected for this port, only the voter and DRO see ballot registration, cast, recast, withdrawal and tally fetches/consumes. The members see the case roll, final winner, credential archive, receipt's roll and outcome, and member-signed successor. The receipt is divulged to members on fetch, even though its create was private. The DRO signs the case and resolver and can create a receipt directly and exercise the public publishing choice without performing the private tally, or collude to create a forked case/consortium. Members explicitly **trust** the DRO's count; a receipt is not cryptographic proof of counted votes or lineage, and this LF 2.3 implementation does not use contract keys to discover the latest ballot CIDs automatically. Case IDs are not globally unique. In small electorates the public result, known participation, timing, credential archive and other external facts can reveal a vote by inference. An auditor or stronger independent tally is separate future work. No interim totals or individual-vote counts are published.

## Reproducing the proof

Use existing SDK 3.5.11 and dpm 1.0.22. CAP prerequisite DARs must already be built for this checkout; BabyDRO never enters the aggregate manifest. From the Concordia root run `sh examples/governance/babydro/test-build-root.sh` and `sh examples/governance/babydro/prepare-dependencies.sh`. Then from a directory **outside** Concordia's aggregate project, with no ancestor `multi-package.yaml`:

```sh
CONCORDIA_ROOT=/absolute/path/to/concordia
DAML_PACKAGE="$CONCORDIA_ROOT/examples/governance/babydro/impl" dpm build --enable-multi-package=no
DAML_PACKAGE="$CONCORDIA_ROOT/examples/governance/babydro/demo" dpm build --enable-multi-package=no
DAML_PACKAGE="$CONCORDIA_ROOT/examples/governance/babydro/demo" dpm test --files "$CONCORDIA_ROOT/examples/governance/babydro/demo/daml/Cap/Examples/BabyDro/Demo.daml" "$CONCORDIA_ROOT/examples/governance/babydro/demo/daml/Cap/Examples/BabyDro/PrivacyProof.daml"
DAML_PACKAGE="$CONCORDIA_ROOT/examples/governance/babydro/demo" dpm test --test-pattern ballotContentPrivacy --transactions-output /authorized/output/dir
```

The first test runs 19 scripts: all 18 original scripts (the 15 baseline scripts, `ballotContentPrivacy`, `resolverCannotForge`, and the isolated topology control `resolverProjection`) plus `genericInterfaces`, covering current generic cast/resolve, wrong-owner rejection, consumed-slot replay, typed request consumption and resolver replay. Packages target LF 2.3; the projection observations below were inspected locally for this port and must be checked against freshly generated output after changes. The `foreignBallotRejected` baseline also checks that a voter cannot mint a forged ballot without the DRO's signature; with the DRO co-signing, a foreign slot is rejected at tally even when the presented voter keys match the case roll. Inspect `transaction-ballotContentPrivacy.html` in the transaction output directory, not merely ACS queries. In the present projection: registration TX25 has member-visible `NameDispute_Enrol` node `#25:4` and sibling private `Ballot` create `#25:6`; TX26/TX28 casts and TX27 withdrawal disclose only to voter a and DRO; resolution TX32 has DRO-only resolver root `#32:0`, private ballot fetches `#32:3` (a, DRO) and `#32:4` (b, DRO), private ballot consumes `#32:10`/`#32:11`, and all-member child `#32:13` with loser archive `#32:23`, consortium successor `#32:29` and ruling `#32:30`. The roll/outcome receipt `#32:12` is divulged to members. No ballot node is divulged to a different member. Node numbers may change after script edits. The control `resolverProjection` contrasts an all-member ancestor ballot fetch (leaks to other members) with the DRO-only resolver root (private sibling fetches; member-visible aggregate child). It also verifies that the child can mint a member-signed successor inside the same transaction.

The local in-memory `dpm test` sequence above remains the fast regression path. A separate opt-in [local container runner](demo/DEMO.md) provides narrative `step 1` through `step 6` and sequential `all`, separately from regression `test`, plus `up`, `logs`, `status` and `down` without modifying shared scripts or requiring BabyCDF to stop. From this directory run `sh demo/run-demo.sh up`, then `sh demo/run-demo.sh all` (or individual steps in order), and finally `sh demo/run-demo.sh down`. `test` explicitly selects the 18 Demo regressions plus `PrivacyProof:resolverProjection`, never the story steps. Do not run build and in-memory tests concurrently against the same package database. It uses project `babydro-live` and localhost port `BABYDRO_LEDGER_PORT` (default 41100). The destination's shared `scripts/sandbox-test.sh` still does not support `INCLUDE_BABYDRO`. This is a local demo only, not an external deployment.

Ignored build exports, downloaded DARs, transaction projections and hermetic-test fixtures are retained under `.build/`, `.daml/` and `.build-root-test-*` for inspection. They are not delivery files. Manual cleanup, if desired, must target only these BabyDRO-generated artifacts and follow the applicable filesystem policy; the scripts do not recursively delete them.
