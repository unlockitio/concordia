# BabyDRO: canton.name governance walkthrough

The CIPs credentials demo owns name requests, registry-issued credentials and their lifecycle. Concordia owns only dispute governance and member entitlement. `Registry.daml` defines a founder-signed `Consortium` holding membership, a demo-local electorate policy, case-opening IDs, and proposals with current-member supporters. Admission, removal and policy changes each require two distinct current members, including the proposer. The consortium does not store ballots, rulings or follow acknowledgements. `Dispute.daml` defines separate founder-signed `Case`, founder-signed `DisputeInvitation`, jointly signed `Ballot` (case authority and voter), and founder-signed `Ruling` contracts. The case holds the authoritative map from voter to active ballot contract ID, and the opening electorate and policy. The ruling records acknowledgements, not credential state.

Opening a case consumes `Consortium.OpenDispute` to check both disputing registries are members, create the case, and record its opening contract ID in the successor's inventory. Governance successors carry that inventory forward. The founder's signature is carried to the case. The first consuming ballot registration records the original case ID on its successor; later case successors preserve it. The founder issues a case- and voter-scoped, pre-signed invitation; that voter independently exercises `DisputeInvitation_Accept` to create a jointly signed ballot and register its ID on the case. That ballot's voter independently exercises `Ballot_Cast` or `Ballot_Withdraw` to replace their ballot and update the case inventory atomically. These voter transactions do not exercise Consortium. A contract ID by itself is **not** authority: the invitation supplies the founder's signature to the accepting voter. This follows the `BallotInvitation`/`PrivateBallot` delegation pattern in the private-majority-vote example. LF 2.2 lacks contract keys, so the caller must use the latest returned case and ballot IDs after each consuming choice; a stale ID fails. The case validates the voter and case identity of each ballot in its inventory at registration and resolution. The case-local `caseId` is not a global uniqueness guarantee across independently opened cases.

`SnapshotAtOpen` and `CurrentMembership` are demo-local policy options. The case freezes its opening policy and eligible voter set. `Consortium_Resolve` is the only resolution entry point: it verifies that the case's opening contract ID is in its own inventory, reads its own active membership, fetches the case's inventoried ballots, and applies the case's frozen policy. No caller-supplied membership set reaches the tally. A snapshot case still counts a removed voter's ballot, including one cast after removal. A current-membership case excludes that voter's ballot at tally; a later consortium policy change does not retarget the case. Exercising a founder-signed Consortium supplies the founder's authority, but does **not** prove that the exercised contract is the unique live governance successor. A requester without founder authority cannot mint a competing founder-signed Consortium; the construction assumes the founder does not mint counterfeit governance state outside the governed succession path. The `founderTrustBoundary` script demonstrates that the founder can create a parallel active Consortium with a copied inventory and favourable membership and successfully resolve through it. This is a founder-trust boundary, not an LF-level uniqueness guarantee. Similarly, the formerly enforced removal guard against removing a party in an open case or with an unfollowed ruling cannot be enforced after cases become independent; it was removed rather than retained as a misleading check. Removing a member requires the two-member threshold but is allowed while its dispute or ruling remains active.

A ruling does **not** change a CIPs name credential. Each affected registry follows by its own action on its own CIPs-owned state; the demo archives the losing registry's credential as that registry and separately records follow acknowledgements. An acknowledgement alone does not prove the external credential action: the journey checks both contract states and asserts unrelated names remain active. Governance cannot verify the existence or truth of a claimed name in CIPs state when opening a dispute; the journey demonstrates the intended ordering.

The source of the name model is in-flight work on the CIPs branch `cip/canton-network-credentials-standard`, consumed as local DAR dependencies, **not** a verified pinned reproducible SHA. Build the CIPs DARs first from `../cips/cn-credentials-standard/demo` with `dpm build --all`. Then, from this repository root:

```sh
dpm build --all
dpm test --package-root examples/governance/babydro/demo
dpm script --dar examples/governance/babydro/demo/.daml/dist/cap-example-babydro-demo-0.1.0.dar --all --ide-ledger
./scripts/sandbox-test.sh
```

The relative DAR paths assume `cips` and `concordia` are siblings, and cannot resolve in a standalone Concordia checkout. Build the sibling CIPs packages before building Concordia; no CIPs source or DAR is vendored here. For a standalone build, supply the CIPs DARs in the same relative layout (without modifying the sources) or change the local dependency paths deliberately. The sandbox runner uploads the built demo DAR and its transitive dependencies.

The naming proposal is [canton-foundation/cips draft PR #209](https://github.com/canton-foundation/cips/pull/209), which has **no assigned CIP number**. The draft motivates dispute governance; it does not prescribe this architecture. Other demo-local choices include three founding registry operators, a fixed two-vote threshold (an off-ledger k-of-n analogue, **not cryptographic threshold signing**), party-based entitlement, a disputer-supplied case ID and reason, and explicit follow acknowledgements. Admission can enlarge the electorate; the threshold remains two as a local simplification.
