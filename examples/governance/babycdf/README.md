# BabyCDF advisory demo

This independent package demonstrates demo-local CAP governance on the ledger and a separate Java 21+ GitHub advisory consumer with an opt-in local sandbox ballot opener. Neither grants Foundation authority nor approves actual Fund funding or milestones. An isolated sandbox script exercises a real Splice coupon allocation against demo-local issuance; it creates no payment or beneficiary mint. The default Java consumer does not read the ledger or cast votes; explicit loopback sandbox modes permit the discovery agent to propose a grant agenda and the independent Reviewer to read active rules.

The Daml demo uses five permanent and two alternate voting identities. Attendance is self-registered in independent `AssemblyAttendance` contracts, co-signed by the CDF (`opener`) and attendee, without changing the assembly or agenda eligibility. Each registration records the assembly CID, window, role and ledger timestamp. After close, the opener presents attendance CIDs for checked identity/group fetch and validation; the result sorts registrations by timestamp then party, records first-registered alternate priority and excludes advisers from the three-voter assembly quorum. Duplicate attendees are rejected at resolution (including distinct contracts for one attendee): this LF 2.2 package cannot use contract keys, so duplicate creation remains possible and resolution requires a complete, externally reconciled CID set; the ledger cannot prove that omitted registrations were included. Member-proposed architecture-rule, grant, and milestone agendas use distinct rounds with real signed `Action` contracts and `IsBallot` ballots. Each of the seven voters has a separately signed ballot and can vote early while the ballot is open. Resolution uses checked `fetchGroup`, `agreedAction`, `agreedSnapshots`, `castsOf`, `consumeBallots`, and CAP `Count.decide (atLeastPresent 3) (shareOfVotes 1 2)`. Abstentions count toward turnout but not the majority tally; absence is not a cast. This 3/7 turnout rule is a demo threshold, not a Foundation policy. Only `Decided Yes` authorizes a CAP `Executable`. The explicitly designated demo opener authorizes and executes it, never an inferred GitHub or Foundation actor. Architecture execution checks the signed registry's authentic key and unchanged version snapshot before advancing the version and creating `EffectiveRule`. Grant and milestone executables have separate agenda subjects and produce separate typed `ApprovedGrantProposal` and `ApprovedMilestone` outcomes. The proposal pin is the full Git blob SHA; the milestone revision is explicitly illustrative, not a verified immutable version of issue #540. An unpinned issue URL is rejected. Neither outcome represents an official decision.

Voting is credential-backed. `Cap.Examples.BabyCdf.Rights` defines BabyCDF-owned `DirectVotingRight` and `RegisteredVotingRight` contracts, each a Canton Network Credentials `Credential` (the registered one additionally a `RegisteredCredential`), with `HasVotingRights` unit weight and a `HasCheckedFetch` group key of issuer, consortium identity and holder. One contract carries exactly one right; there is no `Set` or `Map` inventory of issued rights on the governor or any shared ledger contract, and nothing serializes issuance. A CDF-signed, member-observed `VotingRightInvitation` is accepted by the member alone, so both issuance routes are jointly authorized by the CDF and that member: `AcceptDirect` creates the direct right, and `AcceptRegistered` mints the identical entitlement through the CIPs `CredentialRegistryFactory` implemented by the CDF's `VotingRightFactory`, which accepts only an exact BabyCDF credential view and registration. Revocation is the issuer's own choice; the member cannot archive its right through the credential interfaces. `ResolveAgenda` now takes `rights : [(Party, RightRef)]` and, for each presented right, uses the real CAP `fetchWeightsFromOneContract` plus `fetchChecked` under the claimed key, then requires unit weight, the CDF as credential issuer, the member as sole holder, validity spanning the resolution time, and for a registered right a CDF registry admin with a registration period covering that time. Because the fetch is keyed, a foreign issuer's right, another consortium's claim, another member's credential, an adviser's or an outsider's right cannot be presented as an eligible voter's, and a revoked right has no contract left to fetch. Eligibility itself is still the fixed 5 permanent plus 2 alternate electorate on the governor; a credential claim must match a currently eligible identity and consortium and never extends eligibility. Advisers remain nonvoting.

The resolution rule is exactly one presented right per participating voter: the presented holders must be distinct and must equal the set of voters whose ballots are present (voted or abstained), so a duplicate member credential is rejected at resolution. **Duplicate credentials may be live on the ledger and this package does not prevent duplicate issuance; it only guarantees that two rights for the same member cannot both count in the same resolved round.** This is LF 2.2 without contract keys, and resolution sees only the caller-supplied CID list, which cannot establish uniqueness or completeness of all active credentials for a member; a stronger claim would need an additional authoritative source such as a registry inventory or an off-ledger reconciliation. For that reason the preconditions are fail-closed and explicit: a participating voter with no presented right, a presented right for a non-participating voter, a repeated holder, or any right failing the issuer/holder/validity checks aborts the whole resolution rather than counting a subset. Nothing here makes a global double vote impossible across separate rounds or separate governors. Early voting and the ballot window are unchanged: votes are cast independently while the round is open, and credentials are checked only once, at the intended resolution.

`AgendaGovernor` gains a nonempty `consortiumId` field that the credential claim must match. `ProposeAgenda` arguments are unchanged, and the Java sandbox proposer check reads `opener`, `permanent` and `alternates` by label, so it is unaffected; the Java advisory fixture SHA-256 pin was repinned to the new `RuleVote.daml` bytes after review. The impl package now also data-depends on the local `cips/cn-credentials-standard` interfaces DAR, which must be built before BabyCDF.

Build CAP and auction-demo dependencies from the Concordia root with `dpm build --all`. From the workspace parent, build the standalone template DAR first with `DAML_PACKAGE=/absolute/path/to/concordia/examples/governance/babycdf/impl dpm build --enable-multi-package=no`, then the Script DAR with `DAML_PACKAGE=/absolute/path/to/concordia/examples/governance/babycdf/demo dpm build --enable-multi-package=no` and run `DAML_PACKAGE=/absolute/path/to/concordia/examples/governance/babycdf/demo dpm test`. The impl package `cap-example-babycdf` owns `Cap.Examples.BabyCdf.RuleVote`, `Cap.Examples.BabyCdf.Rights` and the review-clause fixture, without a Daml Script dependency; the demo package `cap-example-babycdf-demo` owns only `RuleVoteDemo` and `CouponDemo` scripts and depends on the impl DAR. BabyCDF is outside the root `multi-package.yaml`; a plain `dpm build` inside Concordia attempts an invalid multi-package build, and `dpm test --package-root` inside Concordia does not target it. The sandbox-only `managerAllocatesIssuedCoupon` compiles the local Splice 0.1.22 DAR (SDK 3.5.2) with BabyCDF SDK 3.5.11 and LF 2.2, then runs the existing CAP vote to produce an `ApprovedMilestone`. A separately allocated sandbox DSO signs `AmuletRules` with a sandbox manager configured and a nonzero Development Fund issuance percentage, bootstraps and advances mining rounds, and calls `AmuletRules_MiningRound_StartIssuing` to create the unclaimed coupon. The manager submits `AmuletRules_AllocateDevelopmentFundCoupon` with read access to DSO contracts. The script checks beneficiary, amount, manager, reason, leftover, and rejects wrong manager and insufficient source funds. It does not impersonate a Foundation DSO, verify the illustrative issue revision, authorize a real Fund grant, or mint Amulet. A live authenticated manager agent controlling the configured party could automatically submit the allocation given appropriate ledger access and DSO contract visibility; this demo does not provide that adapter or those credentials.

A second, independent Java 21 `Reviewer` reads active, versioned `EffectiveRule` contracts through an injected, authenticated read-only `LedgerRuleGateway`, then obtains GitHub evidence through the proposal/milestone discovery API. Its findings carry the rule ID, version, and contract ID. The test gateway is fake and supplies demo contracts; the default gateway returns `BLOCKED` without explicit sandbox configuration. The local sandbox adapter uses Java Ledger API v2 `StateService.GetActiveContracts` at a fixed ledger-end offset with a package-name template filter (required by the Ledger API), a party filter, and an exact deployed package ID check on every returned event. It reads the rule ID, version and clause list from the active `EffectiveRule` payload, not the SHA-pinned source fixture. `EffectiveRule` now stores the voted clause snapshot explicitly, so deploy the newly built demo DAR (which includes the impl DAR), not an older package. Unlike `dpm test`, `dpm script --ledger-host 127.0.0.1 --ledger-port PORT --static-time --dar demo/.daml/dist/cap-example-babycdf-demo-0.1.0.dar --script-name Cap.Examples.BabyCdf.RuleVoteDemo:capRuleAndSeparateApprovals` persists its voted rules to the running sandbox; scripts allocate synthetic parties. Use `dpm sandbox --static-time --ledger-api-port PORT --dar demo/.daml/dist/cap-example-babycdf-demo-0.1.0.dar` with distinct sandbox API ports for isolation. Run `mvn -q exec:java -Dbabycdf.mainClass=org.concordia.babycdf.Reviewer` to see the default blocker, or `mvn -q exec:java -Dbabycdf.mainClass=org.concordia.babycdf.Reviewer -Dexec.args="--local-sandbox 6865 PARTY DEPLOYED_PACKAGE_ID"` against a local `dpm sandbox` with the new DAR uploaded and an active rule created. PARTY must be the actual allocated party visible as a signatory/observer of the contract (e.g. the demo opener or member), and the authenticated ledger user must have `CanReadAs` for PARTY; local insecure sandbox access alone is not production authorization. The package ID must be the deployed 64-hex main package ID from the DAR, never a `#package-name` guess. This plaintext connection is locked to 127.0.0.1 and never enables remote Foundation access. The separate optional comment service requires explicit opt-in, a token, and the allowlisted repository `canton-foundation/canton-dev-fund`. It independently refreshes both active rules and GitHub evidence before considering a comment on PR #184, requires all clauses to pass against a verified proposal blob, and reconciles a deterministic marker against existing comments before posting and after uncertain responses. The unpinned milestone issue cannot yield a definitive positive comment. No CLI enables posting, and no test writes to GitHub. This reviewer does not vote, open ballots, or issue coupons.

The discovery agent's explicit `--local-sandbox PORT DEMO_MEMBER DEPLOYED_PACKAGE_ID GOVERNOR_CID SANDBOX_USER_ID` mode submits `AgendaGovernor.ProposeAgenda` through Ledger API v2 `CommandService` on loopback only. The sandbox user must be authorized to act as the configured demo member; the governor must be active, visible and have that member in its seven-party electorate. The command uses the hard-pinned demo grant subject and the verified full blob SHA, never the PR head SHA. The demo Daml choice only accepts its built-in `proposalSubject` blob `f591787a772848e4537aba5d8ba02be1764647da`; a changed PR blob is blocked until the Daml agenda and DAR are independently reviewed and updated. The ledger clock supplies the one-hour ballot window, including static-time sandboxes. Active `AgendaProposal` and linked active `AgendaAction` ACS snapshots reconcile the round ID and grant subject; uncertain submissions are reconciled once and never blindly retried. This creates an open proposal, not invited voter ballots, votes, approval, Foundation action or coupon allocation. The default mode remains preview-only and issues are still barred from submission. Use a dedicated local sandbox and explicitly configured demo parties/CIDs, not a production endpoint or Foundation identity. For a standalone readback, run `dpm script --ledger-host 127.0.0.1 --ledger-port PORT --static-time --dar demo/.daml/dist/cap-example-babycdf-demo-0.1.0.dar --script-name Cap.Examples.BabyCdf.CouponDemo:bootstrapAdvisoryGovernor --output-file demo/.daml/dist/advisory-bootstrap-output.json` from the BabyCDF directory, then use `_1` as the member and `_2` as the active governor CID. Read the deployed impl package ID from `impl/.daml/dist/cap-example-babycdf-0.1.0.dar` manifest's `Main-Dalf` path (the 64-hex suffix); the demo DAR's main package ID belongs to scripts, not these templates. The demo's `DA.Set.Types:Set` electorate is encoded in ACS as a record with a `map` GenMap of party keys and unit values. Give all Canton sandbox ports unique values if another sandbox runs locally, not just `--ledger-api-port`. After submission, `BABYCDF_SANDBOX_READBACK='PORT MEMBER PACKAGE_ID GOVERNOR_CID USER_ID' mvn test` performs a live ACS round/action readback and rejects a changed blob; absent that variable the test suite uses only fake ledger seams. The GitHub discovery CLI needs public API access or an optional `GITHUB_TOKEN`; an HTTP 403 blocks fresh polling and cannot prove repeat-poll deduplication. Polling in sandbox mode rechecks the grant every interval even if a state file was used for advisory output; a sandbox ACS read failure blocks submission rather than treating an absent result as proof. The independent `Reviewer` remains a distinct live rule-contract read.

The Java consumer discovers Concordia proposal PR #184 and separate milestone issues in `canton-foundation/canton-dev-fund`. It verifies the proposal file's full 40-hex Git blob SHA against retrieved blob bytes using the Git SHA-1 object digest; the PR head commit is a distinct identifier. Issue `updated_at` and body SHA-256 distinguish polling versions but do not pin immutable evidence, so milestone clauses remain `insufficient_evidence` even if text matches. It extracts clause IDs, quotes and anchors from the Daml source only after checking its explicit SHA-256 pin. Its authority marker `pinned_demo_voted_fixture_not_live_ledger` accurately describes its limitation: it does not read a live `EffectiveRule`. Fixture edits require independent review and an explicit SHA-256 repin in Java. Matching verified excerpts pass, contradictory excerpts fail with precedence, and unmatched or unpinned excerpts have insufficient evidence. GitHub text is data only, not executable instructions. The consumer performs no GitHub write, vote or official status update; only explicit local sandbox mode may submit a ledger command. For an isolated repeat-submission check without any GitHub API call, pass `--offline-pr184-repo /path/to/local/canton-dev-fund` alongside `--local-sandbox`. The repository must already contain blob `f591787a772848e4537aba5d8ba02be1764647da`; the seed supplies only the previously verified PR #184 identity and reads that Git object locally. The normal `collect` path still recomputes the Git blob digest from its bytes. The offline run omits milestone discovery and reports `discovery: offline_pinned_pr184_seed_not_fresh_github_poll` plus the matching active proposal/linked-action count. Run the same command twice against one fresh sandbox and synthetic governor: first `submitted_by_ledger_adapter` with count 1, then `already_proposed` with count 1. This does not validate fresh GitHub discovery polling. Default output contains distinct `Grant` proposal and `Milestone` issue ballot command previews. Only the verified proposal blob can form a version-keyed grant round; milestone `updated_at`/body hashes cannot authorize a ballot and are explicitly blocked pending immutable independently verified evidence. The `LedgerApi` ballot-submission seam now has a loopback-only sandbox adapter with governor lookup and active contract reconciliation. The default CLI cannot submit or claim that a ballot exists. A proposal revision has a different round key; ambiguous failure never triggers a blind resubmit. The demo Daml does not enforce a unique round key, so concurrent external submissions cannot be excluded by an ACS precheck; use an isolated sandbox and one submitter. An independent reviewer remains separate from the proposer.

A third Java 21 class, `CouponAllocation`, defines the typed input contract and authority boundary for a Development Fund coupon allocation. It has no ledger, HTTP, or submission seam, so it cannot create a coupon under any configuration. `AllocationInput` carries the source `UnclaimedDevelopmentFundCoupon` contract ids, beneficiary party, demo amount, expiry, the milestone issue reference used as `reason`, the `AmuletRules` contract id, the configured fund manager, the submitting party, the immutable milestone evidence pin, and the `ApprovedMilestone` contract id. Preview output is opt-in and always `BLOCKED`, listing every unmet requirement rather than the first. An approved demo milestone does not make the demo opener the Development Fund manager, the illustrative milestone pin and GitHub `updated_at`/body hashes are rejected as evidence, and no ledger endpoint, authenticated party, or SDK adapter is configured. Run `mvn -q exec:java -Dbabycdf.mainClass=org.concordia.babycdf.CouponAllocation` to see the blocked preview.

The fields come from local inspection of the candidate `examples/lib/splice-amulet-0.1.22.dar`: package name `splice-amulet-0.1.22`, main package ID `fb10433a48c24f30076a7aee03a3e314b7ab02fe9a22e2069e3af92d2b6ac88a`, manifest `Sdk-Version: 3.5.2`. This DAR is not asserted to correspond to any upstream Splice commit; no upstream SHA evidence was obtained, and the demo targets SDK 3.5.11 with `--target=2.2`, and the version pair is now validated locally by the standalone BabyCDF Daml Script compilation and test, not by an upstream revision attestation. `Splice/AmuletRules.daml` declares `nonconsuming choice AmuletRules_AllocateDevelopmentFundCoupon` with exactly `unclaimedDevelopmentFundCouponCids`, `beneficiary`, `amount`, `expiresAt`, `reason`, and `fundManager`, controlled by `fundManager`, and it aborts unless that controller equals the live `optDevelopmentFundManager` in the `AmuletRules` config schedule. There is no `mintAfter` field anywhere in the DAR. Allocation creates a `DevelopmentFundCoupon` whose only choices are `_Withdraw`, `_Reject`, and `_DsoExpire`; this package version exposes no beneficiary mint or collect choice, so allocation stays strictly separate from any beneficiary mint. The choice also archives the listed source coupons and aborts when their total is below the requested amount, which this planner cannot verify without an authenticated ledger read. BabyCDF's `daml.yaml` now references this DAR and the existing auction demo DAR for its local test configuration; neither is a live deployment proof.

Run in `examples/governance/babycdf/java/` with Maven on JDK 21 or later (`java -version` and `mvn -version` must both report Java 21+):

```sh
mvn test
mvn -q exec:java
mvn -q exec:java -Dexec.args="--interval 30 --state-file poll-state.json"
```

`GITHUB_TOKEN` is optional for public read-only requests, subject to anonymous rate limits. Poll intervals are finite and between 0.001 and 86400 seconds. Interrupt with Ctrl-C. Default state is memory-only; an explicit state file must be a direct regular file in the Java project directory, not a symlink, and should be kept private. State replacement is atomic after emission, so a crash between output and save can replay a finding. State contains version identities, not proposal text. Transient GitHub I/O failures leave previous state unchanged. Search and PR file discovery are bounded to one page of at most 100 results each. Output is advisory JSON, not a definitive review or official Fund status.
