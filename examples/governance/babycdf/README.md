# BabyCDF advisory demo

Intake live GitHub discovery requires its own explicit file-backed token, separate
from Reviewer credentials: [secure token setup](demo/GITHUB-TOKEN.md).
Offline `INTAKE_DISCOVERY_MODE=fixture` needs no token and starts no source worker.

Polling from `java/`: `mvn -q exec:java -Dexec.args="--interval 30"` runs the sole Reviewer (blocked without explicit ledger configuration). `--offline-pr184-file` or `--offline-pr184-repo` selects evidence only; active rules still require the authenticated read-only ledger gateway. `--state-file` retains schema-1 preview dedup state. JSON remains on stdout and activity on stderr; `--demo` enables narrated output. Advisory is a shared library, not a runnable polling agent.

Live-network demo: [demo/DEMO.md](demo/DEMO.md) documents the pinned-CIPS Compose network and the full narrated journey. Steps 1-5 run on a wall-clock network: credential bootstrap, one governed rule-change round, a proposal vote, a milestone vote, a real Splice Development Fund coupon allocation with no `setTime`, plus independent security optionals 2-5 (credentials, no quorum, double vote, outsider boundaries). Every individual ledger action prints one greppable `[STEP n][ACTION]` line (`... | grep ACTION`), and expected failures are tagged `[REJECTED]` with the participant error. `all` runs only the Architecture rule vote, step 2; steps 3, 4 and 5 are explicit operator commands and are never part of an aggregate run. Sandbox only: no Foundation authority, no payment and no mint.

The main journey is steps 1–5 (`up` performs step 1; `all` runs only the Architecture rule vote, step 2, and stops there). Steps 3, 4 and 5 stay explicit operator commands, because they vote on existing source rounds and hand the money side a cited approval; `all` never casts a source vote or allocates a coupon. Step 5 runs only on the approval step 4 actually produced and refuses otherwise, including when a blocked or incomplete review produced none. Optional rounds 2-5 need only bootstrap, run alone or in any order, and leave the main anchor unchanged; retired step 6 fails closed with guidance. Voting rounds complete sequentially, with no interleaved stale agenda in step 2. `all` excludes optional rounds. After step 2 has completed and rule v2 is active, `./run-demo.sh opt-step 1` separately proposes a fresh v1-based rule change, casts 3 core YES / 4 ABSENT, resolves APPROVED, then demonstrates refusal of **execution** on snapshot drift. It does not advance the main anchor, so step 3 can follow normally. Live acceptance of this revision is **PENDING**; offline tests and rendered source transcripts are not a live-network run.

Five primary governor seats vote; two credentialed substitutes have no independent votes and their assignment protocol is PENDING. Every round accounts for exactly five primary ballots, including absent ballots. Three distinct valid primary YES votes approve immediately, before or at the deadline. Two YES votes never approve, including with abstentions or absences. Fewer than three YES votes remain pending before closure; early rejection is not supported. Voters are selected from the governor's recorded `permanent` set through `coreQuorum`, never ballot order. Opening requires actual rights for all five primaries, valid now and strictly beyond `closesAt`; resolution independently checks participating rights at resolution and closing time. Fresh bootstrap defaults to 30-day factory-registered credentials for all seven members, configurable with `BABYCDF_CREDENTIAL_VALIDITY` (`1h` through `365d`, for example `2d`). Existing rights are never automatically extended. See [demo/PRIMARY_PROTOCOL.md](demo/PRIMARY_PROTOCOL.md).

INITIAL/FINAL STATE report scoped active state, not archived history. A zero count is neutral. Step 1 has no demo witness yet and reports participant party/user lists only, explicitly not contract counts. Later steps query actual visible contracts and interfaces.

This independent package demonstrates demo-local CAP governance on the ledger and a separate Java 21+ GitHub advisory consumer with an opt-in local sandbox ballot opener. Neither grants Foundation authority nor approves actual Fund funding or milestones. An isolated sandbox script exercises a real Splice coupon allocation against demo-local issuance; it creates no payment or beneficiary mint. The Daml demo uses five permanent and two alternate voting identities. Attendance is self-registered in independent `AssemblyAttendance` contracts, co-signed by the CDF (`opener`) and attendee, without changing the assembly or agenda eligibility. Each registration records the assembly CID, window, role and ledger timestamp. After close, the opener presents attendance CIDs for checked identity/group fetch and validation; the result sorts registrations by timestamp then party, records first-registered alternate priority and excludes advisers from the three-voter assembly quorum. Duplicate attendees are rejected at resolution (including distinct contracts for one attendee): this LF 2.3 package cannot use contract keys, so duplicate creation remains possible and resolution requires a complete, externally reconciled CID set; the ledger cannot prove that omitted registrations were included. Member-proposed architecture-rule, grant, and milestone agendas use distinct rounds with real signed `Action` contracts and `IsVoteRecord` vote records. Each of the five primary voters has a separately signed ballot and can vote while the ballot is open; the two credentialed substitutes have no independent ballots. Resolution retains checked `fetchGroup`, `expectUniformAction`, `expectUniformSnapshots`, validated interface `casts`, and `consumeVoteRecords`. Approval explicitly requires three primary YES votes; CAP counting remains the nonapproval fallback at closure and cannot approve two YES votes. Abstentions count toward turnout but not the majority tally; absence is not a cast. The approval threshold is three distinct valid YES votes from the five primary seats; substitute assignment remains unsupported. Only `Decided Yes` authorizes a CAP `Executable`. The explicitly designated demo opener authorizes and executes it, never an inferred GitHub or Foundation actor. Architecture execution checks the signed registry's authentic key and unchanged version snapshot before advancing the version and creating `EffectiveRule`. Grant and milestone executables have separate agenda subjects and produce separate typed `ApprovedGrantProposal` and `ApprovedMilestone` outcomes. The proposal pin is the full Git blob SHA; the milestone revision is explicitly illustrative, not a verified immutable version of issue #540. An unpinned issue URL is rejected. Neither outcome represents an official decision.

Voting is credential-backed. `Cap.Examples.BabyCdf.Rights` defines BabyCDF-owned `DirectVotingRight` and `RegisteredVotingRight` contracts, each a Canton Network Credentials `Credential` (the registered one additionally a `RegisteredCredential`), with `HasVotingRights` unit weight and a `HasCheckedFetch` group key of issuer, consortium identity and holder. One contract carries exactly one right; there is no `Set` or `Map` inventory of issued rights on the governor or any shared ledger contract, and nothing serializes issuance. A CDF-signed, member-observed `VotingRightInvitation` is accepted by the member alone, so both issuance routes are jointly authorized by the CDF and that member: `AcceptDirect` creates the direct right, and `AcceptRegistered` mints the identical entitlement through the CIPs `CredentialRegistryFactory` implemented by the CDF's `VotingRightFactory`, which accepts only an exact BabyCDF credential view and registration. Revocation is the issuer's own choice; the member cannot archive its right through the credential interfaces. `ResolveAgenda` now takes `rights : [(Party, RightRef)]` and, for each presented right, uses the real CAP `fetchVotingRightsFromOneContract` plus `fetchChecked` under the claimed key, then requires unit weight, the CDF as credential issuer, the member as sole holder, validity spanning the resolution time, and for a registered right a CDF registry admin with a registration period covering that time. Because the fetch is keyed, a foreign issuer's right, another consortium's claim, another member's credential, an adviser's or an outsider's right cannot be presented as an eligible voter's, and a revoked right has no contract left to fetch. Eligibility itself is still the fixed 5 permanent plus 2 alternate electorate on the governor; a credential claim must match a currently eligible identity and consortium and never extends eligibility. Advisers remain nonvoting.

The resolution rule is exactly one presented right per participating voter: the presented holders must be distinct and must equal the set of voters whose ballots are present (voted or abstained), so a duplicate member credential is rejected at resolution. **Duplicate credentials may be live on the ledger and this package does not prevent duplicate issuance; it only guarantees that two rights for the same member cannot both count in the same resolved round.** This is LF 2.3 without contract keys, and resolution sees only the caller-supplied CID list, which cannot establish uniqueness or completeness of all active credentials for a member; a stronger claim would need an additional authoritative source such as a registry inventory or an off-ledger reconciliation. For that reason the preconditions are fail-closed and explicit: a participating voter with no presented right, a presented right for a non-participating voter, a repeated holder, or any right failing the issuer/holder/validity checks aborts the whole resolution rather than counting a subset. Nothing here makes a global double vote impossible across separate rounds or separate governors. Early voting and the ballot window are unchanged: votes are cast independently while the round is open, and credentials are checked only once, at the intended resolution.

While an agenda is open the Reviewer also prints one advisory recommendation per agenda per rule version, for example `[reviewer] RECOMMENDATION proposal_pr <roundId> under architecture-review v2 (cid ...): APPROVE - compose-with-asset-layer: pass; evidence: offline pinned PR#184 blob f591787a77... (advisory only, members decide)`. The mapping is conservative: all clauses pass gives APPROVE, any failure gives REJECT, any insufficient evidence gives HOLD, and a missing rule or empty finding set gives BLOCKED; a failure outranks missing evidence and an unknown status is never read as approval. Each line cites the rule id, version and contract, the evidence pin and an advisory label. The clause text criterion is ledger data: `ReviewClause` carries `criterion`, `requiredPhrases` and `forbiddenPhrases`, and the Reviewer evaluates the pinned PR #184 blob against whatever the active `EffectiveRule` states, so the only constants in agent code are the matching mechanics. Matching is deterministic literal phrase matching after case folding and whitespace normalization; no semantic or LLM-assisted understanding is performed or claimed, and LLM-assisted evaluation remains planned. Findings are `pass`, `fail` naming the missing or forbidden text, or `insufficient_evidence` when no verified pinned text exists, and each cites the clause id, rule version and criterion. The v1 seed rule requires an `independent security audit`, a phrase the real proposal never contains (it commits only to `auditable contract state`), so the agent reports `fail` and recommends `REJECT` under v1. The v2 rule voted in step 2 replaces that clause with `auditable-state-and-acceptance`, which the same text satisfies, so the agent re-evaluates and recommends `APPROVE`: the verdict changes because the rule changed, not the evidence. Step 2 votes to activate the predefined v2 clause set, and activation publishes those clauses as ledger data; a vote does not author arbitrary clause text, it decides which published clause set is authoritative. The Java Reviewer and the on-ledger `ApplyRule` are two separate advisory evaluators with different inputs: the Reviewer does literal phrase matching over the full pinned document, while `ApplyRule` tests membership in a curated `PinnedExcerpt` list. That is why the audit clause can read `fail` in the agent log and `InsufficientEvidence` in a ledger `RuleApplication` without contradiction, and neither result gates the agenda; the hard-coded `validAgenda` pin does that. It discovers visible agendas as a read-only observer of `AgendaProposal`, which needs no extra right beyond the existing `CanReadAs`. The demo's `babycdf-agent` ledger user holds exactly two rights, `CanReadAs <member>` and `CanReadAs <opener>`, asserted by equality at bootstrap; it has no `CanActAs`, so it is incapable of casting a vote or submitting anything. An agenda is matched to a review only when both its subject URL and its exact subject body equal the revision the review pinned: a rule-change (Architecture) agenda reuses the proposal URL but carries its own design text, so URL-only matching would falsely approve it. Non-matching agendas report `BLOCKED - not reviewable against proposal evidence`, and agendas past `closesAt` are skipped. The recommendation is advisory and drives nothing: the demo voters are scripted and vote Yes regardless, so the agent's opinion and the ledger outcome are deliberately not coupled. This reviewer does not vote, open ballots, or issue coupons.

### Rule documents

Rules are versioned JSON under `rules/`. The ledger stores only location,

### Optional real supplemental LLM assessments

See [LLM configuration and verdict semantics](demo/LLM.md) for the recommended `LLM_API_KEY_FILE` provisioning, `BABYCDF_LLM_ENABLED=1`, and the exact command to recreate **only Reviewer**, preserving the ledger and Intake. Exact PASS/FAIL/INCONCLUSIVE/NOT_APPLICABLE clause verdicts are machine-validated and aggregated in code; separately labelled advisory commentary cannot influence them. Reproducibility is cache-based, not mathematical determinism. The Compose `/tmp` tmpfs cache is cleared when the container stops or restarts, so valid verdicts can be paid for again, bounded to four calls per process. Persistence across process restarts applies only to direct CLI runs using a normal persistent `/tmp`.

Export `BABYCDF_LLM_ENABLED=1` and provision `LLM_API_KEY` securely in the invoking environment, then run either Java agent normally (or start the documented Compose agents profile). Both container agent services forward only BABYCDF_LLM_ENABLED and explicit LLM_API_KEY/LLM_BASE_URL/LLM_MODEL settings, not ambient OPENAI or OMNIROUTE credentials. CLI Settings retain their legacy provider fallbacks. Do not print resolved Compose configuration with credentials present. Without explicit opt-in or a configured key, no provider call occurs; one disabled notice is emitted. No live calls are needed for tests.

Gertrudes defaults remain `https://ai-gateway.unlockit.io/v1` and `claude/claude-sonnet-4-6`. `LLM_BASE_URL`, `LLM_MODEL`, and `LLM_API_KEY` override provider defaults; existing `OPENAI_*` / `OMNIROUTE_API_KEY` fallbacks retain their Settings precedence. Never put literal keys in tracked files.

Each process reuses one client across polls and makes at most four uncached assessments (at most four HTTP attempts in production; injected retry tests allow at most eight). Evidence bundles include full accepted file contents within a 200 KiB aggregate text budget, with excluded files explicitly making completeness=false. A 2,000,000-unit conservative reservation ceiling uses actual transmitted request UTF-8 bytes plus 2048 output tokens per possible attempt; unused reservations are not refunded. Cache lookup precedes reservation, so hits consume no call or token budget. Full rule clauses are never silently truncated. Exhaustion returns explicit INCONCLUSIVE. Only schema-parsed provider responses are persisted; transport, HTTP, timeout, budget and local failures are deduplicated only in memory and retried after process restart. Restart resets the process-local budget. Valid cached verdicts survive direct CLI process restart on normal `/tmp`, but not a Compose container stop/restart because its `/tmp` is tmpfs. This is not a global spending guarantee: manual or orchestrated restarts reset it. Only verified immutable public proposal text is sent; unpinned milestones remain insufficient evidence and are not sent. Reviewer includes the active ledger rule clauses; Advisory uses its pinned source rule unless a read-only ledger rule is configured. If readback succeeds but supplemental rule selection is unavailable or ambiguous, supplemental assessment is skipped with a context-unavailable notice (not a provider attempt); deterministic evaluation continues. Ledger readback I/O failures still propagate before polling-state mutation. Text is explicitly untrusted and no provider tools are offered. Advice and concise summaries are supplemental, never deterministic findings, ballot authority, execution or publication. One result line identifies subject, rule version, exact verdicts, returned model, cache status and latency alongside deterministic findings; optional commentary is separately labelled advisory and not verified. Full prompts/responses and credentials are never logged.

Reviewer/Advisory use the same validated `INTAKE_GITHUB_TOKEN_FILE` secret as Intake when the optional agents GitHub auth overlay is selected; otherwise reads are anonymous. Ambient `GITHUB_TOKEN` is ignored. The credential adds no GitHub write or ledger authority. Poll intervals are finite and between 0.001 and 86400 seconds. Interrupt with Ctrl-C. Default state is memory-only; an explicit state file must be a direct regular file in the Java project directory, not a symlink, and should be kept private. State replacement is atomic after emission, so a crash between output and save can replay a finding. State contains version identities, not proposal text. Transient GitHub I/O failures leave previous state unchanged. Search and PR file discovery are bounded to one page of at most 100 results each. Output is advisory JSON, not a definitive review or official Fund status.

### Deterministic presence collection

When the effective verified rule contains a `PRESENCE_REQUIRED` clause, agents collect the bounded verified file bundle even when LLM assessment is disabled. Deterministic findings therefore do not depend on the LLM switch. Contradiction-only rules retain the existing supplemental collection gating. Blob and bundle caches bound repeated GitHub reads. Absence still requires pinned, reread-consistent, complete and affirmatively valid evidence. The dedicated rules root defaults to `../rules` from the Java working directory (`/app/rules` in the image); seeded `rules/` locations are resolved relative to that root.

Daml-side commit-reference validation remains deferred because adding it changes the package. Seed hashes are checked against exact rule document bytes without changing Daml.

## Host HTTP and gRPC ledger access

Both unauthenticated demo APIs are published on host loopback only: gRPC `127.0.0.1:${LEDGER_PORT:-41000}` and HTTP JSON `http://127.0.0.1:${LEDGER_HTTP_PORT:-41001}`. Never expose these mappings on 0.0.0.0 or a public interface. `up` validates distinct ports in 1024–65535 and probes both loopback binds before starting. A busy port requires an explicit override. The pinned Canton config already listens on container 0.0.0.0:7575; host loopback publication is the security boundary. Applying the new mapping requires recreating Canton at the next user-authorized down/up; no running stack was changed.
