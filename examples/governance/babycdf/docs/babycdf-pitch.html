BabyCDF
Voted rules, agentic review

Community-voted rules drive agentic review of grant proposals and milestones. The ledger holds voted proof of which rules are in force, and agents evaluate only against them. Humans decide. The ledger enforces.
Today the clause text lives on the ledger in EffectiveRule and a vote activates a predefined clause set. Rule content in GitHub, bound by a repo/commit attestation, is planned architecture.

sandbox prototype — no production deployment or Foundation authority built on Concordia: the Daml Canton Allocation Primitives no production authority · no real payment

Speaker notes

BabyCDF is a working governance prototype, not a product launch. One sentence to open with: the rules the community votes on are the only rules an agent is allowed to review against. Say plainly up front: this is a sandbox prototype with no production deployment or Foundation authority, and no money moves. Add the one nuance that keeps the rest of the deck honest — today the clauses live on the ledger and a vote activates a predefined clause set; the GitHub attestation model you will see on the next slides is planned architecture, not running code. That honesty is what makes the rest of the deck credible.
Problem

Reviewing proposals and milestones by hand does not scale — and does not audit

What goes wrong today
  • Manual review. Proposals and milestones are read case by case, under time pressure.
  • Implicit rules. Criteria live in people's heads, threads and changing documents.
  • Inconsistent application. Two reviewers, two readings of the same criterion.
  • Mutable evidence. A PR or issue can change after it was reviewed.
  • Hard to audit. "Why was this approved?" has no reconstructable answer.
And automation is the wrong fix — as usually built
  • Untrusted. An LLM that reads "the rules" from a moving document proves nothing.
  • Or too powerful. An agent that can approve or pay is an unaccountable authority.
  • No binding between rule and verdict. A verdict that cannot name the exact rule version it applied is an opinion.
The gap is not intelligence. It is provable inputs: which rules were in force, and which evidence was judged.

Speaker notes

Frame the problem as an evidence problem, not a labour problem. Reviewers are not the weak link; the weak link is that nobody can prove afterwards which rule text was applied to which exact artefact. Then name the trap: the usual answer is "add an AI reviewer", which either nobody trusts or which quietly becomes the decision-maker. BabyCDF refuses both.

Speaker notes

Open by saying this lane diagram is the planned architecture, so nobody leaves thinking it runs today. What runs today is the ledger half: the clause text sits on the ledger in EffectiveRule, a credentialed vote activates a predefined clause set, and the stale check at step 4b is real. Proof of rules in force planned

Before reviewing anything, the agent proves which rules it may use

Planned mechanics. Today: the agent reads the active EffectiveRule from the ledger and checks the package ID and version; there is no repo/commit attestation to hash-verify against.
The Reviewer's check sequence — every single review
1Read the active attestation on the ledger
2Fetch the rules from GitHub at exactly that commit
3Verify the blob hashes against the attestation
4Only then evaluate the clauses
Outcomes
✓ verified
Hashes match the attestation. Review proceeds, citing the rule version and short SHA.
⚠ unratified rule change at HEAD
Newer rule commits exist in the repository but carry no vote. They are ignored; the agent keeps using the ratified version and flags the divergence.
⛔ BLOCKED — fail closed
Hash mismatch, or no attestation at all. The agent does not guess and does not fall back to HEAD. It refuses to review.
Every verdict is traceable: rules v2 @ 3f9a1c2 ✓ verified — the rule version and the short commit SHA travel with the opinion. The commit SHA and clause results shown here are illustrative examples.

Speaker notes

This is the trust slide. The agent has no authority to decide which rules apply; it can only read what was voted. Spell out fail-closed: a hash mismatch or a missing attestation produces BLOCKED, never a best-effort review. And explain why "unratified HEAD is ignored, not used" matters — it means merging a rule change to the repository is not a governance action. Only a vote is. Flagging it keeps the divergence visible instead of hidden.

Speaker notes

Two details to call out. The evidence pin is a Git blob SHA-1 of the content reviewed — deliberately distinct from the PR head commit, so later pushes cannot silently change what was judged. And the clause evaluation is three-valued on purpose: "fail" must name the text it could not find, and "insufficient evidence" is a first-class answer rather than a reluctant pass. Be precise about two things. The clauses come from the ledger today, not from a GitHub attestation — that is the planned evolution, and step 3 is labelled accordingly. And the agent's output goes to the terminal and the log only: nothing is posted to GitHub, so step 5 is marked planned. The agenda, the quorum, the tally and the approval are the ledger's.

Speaker notes

The one-liner: in this design, merge permission is not governance permission. Anyone with write access to the repository can change the text; only a vote can change the rules. That split is what lets you keep rules readable and reviewable in GitHub without making the repository's access control the de facto constitution.
Trust boundaries

Each party does exactly one job

GitHub
Holds the rule content.
  • planned Versioned, human-readable rule files and clauses
  • Reviewed the way code is reviewed
  • Write access ≠ governance authority
  • Today: GitHub holds the proposal evidence, pinned by blob SHA; the rules live on the ledger
Ledger
Holds the voted proof — and enforces.
  • Today: the clause set itself, versioned in EffectiveRule; a vote activates a predefined set
  • Active rule pointer; stale changes rejected
  • Agendas, quorum, tally, approvals
  • planned Attestation: repo, commit, blob hashes, version
Agents
Advise only.
  • No voting rights, no approval power (readAs only)
  • Today: evaluate only against the active ledger clause set
  • Fail closed with no authenticated ledger
  • planned Hash-verify against the attestation; fail closed on mismatch
Members
Humans decide. Credentialed members vote; agents produce evidence-bound opinions that make the vote better informed, never a substitute for it. Agents advise → humans decide → the ledger enforces.

Speaker notes

Use this slide to answer the governance objection before it is raised: "are you letting an AI decide who gets funded?" No — the agent cannot vote, cannot approve, cannot pay, and refuses to act when its inputs are unproven. It holds readAs only, so it is incapable of casting a vote, not merely restrained. Its entire power is to read the active ledger clause set and write an opinion with citations. Mind the today-versus-planned split in the ledger and agent columns: today the ledger holds the clause set itself and the agent evaluates against that; the repo/commit attestation and the hash-verification refusal are planned. Keep the four-part refrain tight: GitHub holds content, the ledger holds proof, agents advise, humans decide.
Demo script

What we show, including what we deliberately refuse

Happy paths
  • Ledger-resident clause sets: v1 fails on a missing required phrase; a vote activates the predefined v2, which passes
  • Deterministic literal phrase matching against the pinned PR #184 text — no semantic or LLM evaluation
  • Recommendations printed to the terminal and log only; nothing is posted or published
  • Read-only agents: readAs only, no actAs, so they cannot vote or submit
  • Agenda, credentialed vote, quorum and tally → ApprovedGrantProposal
  • Milestone vote → real sandbox DevelopmentFundCoupon allocation (not a payment, not a mint)
Blocked paths — working today
  • Not reviewable — the milestone subject has no reviewed evidence (advisory only)
  • Invalid credential on a vote attempt
  • No quorum — fewer than 3 present
  • Stale rule change — outdated base version
  • Double vote from the same member
Blocked paths — planned design
  • Unratified rule change present in the repository: ignored and flagged
  • Rule hash mismatch against the attestation: review refuses to run (BLOCKED)
Shown as design, not as a demo claim.

Speaker notes

Demo the refusals, not just the approvals. The blocked paths in the middle column run today and are the most persuasive part of the session. Be scrupulous about the third column: the unratified-change flag and the hash-mismatch block are planned design, not running code. If asked, say exactly that — the credibility of the whole deck rests on not blurring this line. The strongest moment in the happy-path column is the first bullet: the same pinned proposal text fails under rule v1 and passes under v2, because the voted rule changed and nothing else did. Be equally clear that the agent only prints to the terminal — there is no posting anywhere — and that the matching is literal phrase matching, not comprehension.

Limitations · next steps · ask

What this prototype does not do — and what we want next

Limitations
  • Credential uniqueness and attendance reconciliation are handled externally, not by the contracts
  • The milestone evidence is illustrative: the agent recommends BLOCKED, but that is advisory and the scripted vote still approves the curated milestone
  • The provenance of the local Splice DAR is incomplete
  • No production authority and no payment: the coupon allocation is real but sandbox-only — neither a payment nor a mint; the separate Java CouponAllocation planner stays a blocked preview
  • Votes are cast by scripted synthetic parties, not independent human members
Next steps
  • Move EffectiveRule to a GitHub attestation (repo, commit, hashes, version)
  • Ship the rule-change watcher and hash verification before every review
  • Add the unratified-change flag and immutable milestone evidence
  • Add an authenticated ledger adapter
  • Introduce LLM-assisted clause evaluation, advisory and pinned
The ask
  • Review the governance model: rules in GitHub, voted proof on the ledger
  • Confirm the rule-change and quorum parameters as a community
  • Agree a sanctioned golden-copy rules repository and its review process
  • Clear DAR provenance and an authenticated environment for the next milestone
Agents advise → humans decide → the ledger enforces. Every verdict cites its rule version and commit, or it is not a verdict.

Speaker notes

Close with the limitations stated as deliberate boundaries rather than as excuses: external credential uniqueness, illustrative milestone evidence, incomplete DAR provenance, no authority and no payment. Then the ask is about decisions only a community can make — which repository is the golden copy, what the quorum parameters are, and what an authenticated environment would look like. Repeat the refrain and stop there.
