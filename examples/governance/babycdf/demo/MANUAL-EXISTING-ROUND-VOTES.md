# Manual voting on existing source rounds

Steps 3 and 4 are explicit operator actions by the synthetic demo opener and actual selected ballot holders. They do not submit an Intake request, create a source credential, open a proposal, change authority, extend a deadline, or reopen an expired round. Step 5 is also an explicit operator action, available as `./run-demo.sh step 5`, and it is excluded from `all` for the same reason steps 3 and 4 are.

Step 5 acts only on the approval step 4 actually produced. Step 4 records that approval's identity (contract id, subject URL, content version and source round id) in its own result file, and step 5 reads that file, re-binds the identity to live ledger state and refuses if the approval is absent, archived, mismatched or ambiguous. A step 4 that recorded votes without an executable approval, including a `BlockedPin` round, carries no approval, so step 5 refuses instead of citing an illustrative milestone. There is no fallback to a subject constant and no synthetic run id.

Step 5's refusals are checked twice: a read-only prevalidation runs before the one-shot marker is written, so a definite pre-submission refusal strands no permanent marker, and the allocating entry point repeats the identical binding because the first check cannot close the time-of-check/time-of-use window. After any attempt that may have submitted, the marker remains permanent and is reconciled read-only, exactly as for the other steps.

Step 5 also refuses a handoff that belongs to another run. The run anchor is selected by run id alone, so a step-4 result copied from a different network, including a perfectly valid one whose own step 5 is still pending, would otherwise bind to that run and allocate against its approval. Before the prevalidation script and before any marker or lock exists, the runner compares the handoff's run id with the run id `up` recorded in `run-id.json`, and a mismatch, a missing `run-id.json` or a malformed one refuses outright. The comparison lives in the runner because a Daml script input cannot know which run the host bootstrapped.

Steps 4 and 5 each hold their own exclusive process lock, at `step-4.lock` and `step-5.lock`, for the whole attempt. Step 5 requires one for the same reason step 4 does: the one-shot marker is written only after the prerequisite guard, so two simultaneous `step 5` commands would otherwise both pass that guard and both allocate a coupon from a single approval. The ledger does not prevent this either, because the allocation is submitted before the run anchor advances; the anchor is deliberately not advanced earlier, since that would strand a retry after a failed allocation. After acquiring the lock, each run rechecks the marker and the result, so a late loser refuses instead of submitting again. These locks are cooperative and process-scoped: they serialize runner commands, which is the supported case, and they cannot exclude an external ledger client, which is not supported.

An interrupted step 5 is retained exactly like an interrupted step 4: the lock records `uncertain`, the marker stays, and nothing is cleared automatically. `recover-step4-marker` is step 4 only. It takes the step-4 lock and clears only the step-4 marker, never a step-5 marker or lock, because proving that a coupon allocation never reached the ledger is outside what its log check establishes. An uncertain step 5 therefore stays blocked until `down`.

Step 3 requires one existing, verified, pinned PR184 round. Step 4 requires one existing pinned milestone540 round with a DeliveryPin and an actual approved, pinned PR184 prerequisite. Missing or ambiguous evidence is an error, not a reason to create a replacement. An immutable source snapshot may remain usable after its original source credential is archived.

Before voting, the script verifies the proposal, action, copied source and round receipt agree, including subject URL and fingerprint. The electorate must match the current governor's five primary seats. Two credentialed substitutes retain observer visibility but have no independent votes; their assignment protocol is PENDING. Selected voters are actual primary parties with existing credential references, not inferred login names.

For a round with no ballots, invitation is allowed only before its deadline. Complete existing ballot sets are reused. Partial or duplicate sets fail closed. Only absent selected votes are cast; existing YES votes are verified and never recast. Conflicting votes refuse the operation.

The command queries the existing public `VoteTopic` and binds its CID and view to exactly one verified `AgendaProposal`, receipt, source snapshot and executable pin. Before any invitation or cast, it checks the deadline, the complete existing ballot set, absent votes and the selected primary holders' rights through the deadline. It invites ballots only when none exist, casts three primary YES votes, resolves the existing proposal immediately and executes the CID returned by `ResolveAgenda`. Milestone #540 also requires an actual pinned approval of PR184.

Each host command is one-shot. An existing attempt marker or result file refuses another submission. If submission is uncertain, stop and reconcile the ledger manually using read-only evidence; do not automatically retry, recast, reset the network or delete markers. There are no manual phase-checkpoint contracts or automatic resume. A successfully resolved topic is normally consumed. A missing or ambiguous existing target fails closed; the command never opens or reopens a round, fabricates source evidence, or extends a deadline.

## Credential expiry is not extended

Fresh bootstrap credentials default to 30 days, configurable with `BABYCDF_CREDENTIAL_VALIDITY` as whole hours or days from `1h` through `365d` (for example `2d`). All seven are factory registered. Before opening, all five primary rights must be valid both now and strictly beyond `closesAt`; expiry equal to the deadline is rejected. Fresh 30-day rights cover a fresh 21-day round, but aged rights or a longer window may not. Resolution independently checks participating holder rights at resolution and closing time. Existing contracts are not modified. This command does not renew, grant or extend credentials, reset deadlines, or create replacement authority. A coverage failure requires appropriately valid credentials through the separately authorized authority process before opening.

Offline tests use preopened short-window rounds and advance test time within credential validity. Such fixtures are not live evidence.
